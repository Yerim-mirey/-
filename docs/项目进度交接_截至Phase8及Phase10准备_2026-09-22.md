## 5. 本轮发现并修复的问题（含设计决策）

### 5.1 Phase 7 遗留：具体意图没有被相应事实支撑（`caa1d77`）

**问题：** Runner 只按 `needs_full_diagnosis` 二分取证。`accessibility_query` 只拿到 Location + POI，**没有任何步行时间事实**却以 `completed/normal` 结束；`blindspot_query` 只拿到 POI 计数，被当成盲区结论。

**修复（先写失败测试再改）：**

| 意图 | 修复后取证路径 |
| --- | --- |
| `accessibility_query` | Location → POI → `calculate_walking_times`；POI 为空时不发 Routing 请求，写 `NO_ROUTING_TARGET` warning |
| `blindspot_query` | Location → Diagnosis（复用 `diagnose_community` 内部的等时圈/盲区阶段） |

**契约修正：** `app/schemas/agent.py` 中 `blindspot_query` 的标志期望改为 `(True, False, False)`。原因是 Brief 校验器把该意图钉死在"不做完整体检"，不改就无法让它取得 Diagnosis 事实。这是**对公共契约的语义修正**，Phase 8 交接文档明确允许（"应在 Phase 8 明确修复取证路径，或限制产品支持范围"）。

**盲区为什么不自己编排低层 Tool：** `BlindspotRequest` 要求上游等时圈结果，等时圈需要路由函数，而 `ToolGateway` 不暴露路由函数——只有走 Diagnosis 才符合"不让 Agent 编排低层 GIS Tool"的边界。

### 5.2 真实调用暴露：思考模式吃满 JSON 预算（`290bb4e`）

**问题：** 首次真实冒烟 planning/reviewer 双双失败，用量显示 `completion_tokens=4096` 正好等于 `max_tokens`，其中 2499 是 reasoning tokens——JSON 输出被截断。

**根因（查官方文档确认）：** `deepseek-flash` 的思考模式**默认开启、默认 effort 为 high，且 reasoning tokens 计入 `max_tokens`**。

**修复：** 默认关闭思考（`thinking: disabled`）、预算提到 8192、检测 `finish_reason=length` 时抛 `LLMOutputTruncated` 子类以区分截断与格式错误。修复后 `completion_tokens` 由 4096 降到 69。

**这类问题只有真实调用会暴露，受控模型测试不可能发现。**

## 6. 接手前必读：已知坑与边界

### 6.1 代码/工具层面的坑

1. **脚本必须用 `-m` 运行。** `python scripts/xxx.py` 会因 `sys.path` 缺仓库根目录而 `ModuleNotFoundError: No module named 'app'`。**这是仓库既有问题，`verify_diagnosis_live.py` 等旧脚本同样如此。** 正确写法：`python -m scripts.verify_agent_llm_live`。
2. **Mock Tool Gateway 只服务 `contracts/v1` 的精确样例。** 请求逐字段不同就抛 `MockScenarioError`。特别是 `contracts/v1/location-request.example.json` **只有地址型**，坐标型 `resolve_location` 在真实 Mock 下会失败；场景测试需要自建交换（`tests/e2e/helpers.py` 的 `location_exchange` 已支持坐标）。
3. **夹具中心点的两个不同取值。** 地址解析夹具中心是 `(121.506123, 31.282456)`（与所有 Diagnosis 样例一致），而 `contracts/v1/poi-search-request.example.json` 的 POI 中心是 `(121.5081, 31.2809)`。`tests/e2e/helpers.py` 已按"POI 与 Routing 都用解析后的地址中心"处理，改夹具时别搞混。
4. **`EvidenceBundle` 禁止 Diagnosis 与低层结果并存。** 所以体检证据里没有 POI/Route，盲区只能靠 Diagnosis。
5. **`0` 是确认没有，`null` 是未知。** 未请求的设施类别计数必须是 `null`，否则 Mock 校验会报 "POI counts differ from request or returned facilities"。未知计数必须带 `PARTIAL_POI_RESULTS` warning。
6. **`AgentRunState` 的中间态约束很强。** 含 `missing_information` 的 Brief 只能处于 `waiting_for_input` 或 `failed`，所以 Orchestrator 节点必须**一次原子更新**写完状态与 Brief（不能先 `running` 再改）。
7. **Tool 重试预算与补证据共用一个计数器。** `MAX_TOOL_RETRIES=2` 意味着"首次取证 + 最多 2 次重取"；补证据回路最多换 3 个 bundle ID，之后在 REVIEW 升为 `with_limitations`。不要误以为是 bug。
8. **未配置的 Mock 交换按"可重试的 `GATEWAY_ERROR`"处理**，会消耗重试预算后以 `failed` 终止。

### 6.2 语义边界（不要越界宣称）

1. **`completed` 只表示 Runtime 走完流程且有证据，不代表用户的问题被回答，更不代表真实服务质量。** 这是 Phase 8 建立断言方式的核心动机。
2. **"输出符合 Schema" ≠ "内容正确"。** 真实模型冒烟的 9/9 只说明前者。冒烟中 reviewer 返回 `revision_required` 并列出 3–4 个问题是**正确行为**（冒烟提案故意让市场证据支撑药店/小学建议）。
3. **真实模型语义质量未评测。** 意图准确率、规划是否超出证据、审查是否漏判，都需 Phase 10 的评测集与人工抽样。
4. **真实百度和真实 Gateway 都未验收。** 离线全绿不能替代。
5. **1 次 Planning 拒绝未解释。** 样本极小，不能据此判断真实模型输出稳定性达标。

### 6.3 明确不做（架构冻结，别当遗漏）

Docker、CI、持久化、Redis、队列、长期记忆、RAG、额外 Agent（架构第 16、17 节）；`app/agent_runtime/validation.py` 是架构第 20 节的预留文件，交接文档未把它排入任何阶段。

### 6.4 安全提示

`DEEPSEEK_API_KEY` 曾在某次对话中以明文出现。**建议在 DeepSeek 控制台轮换一次**，新密钥只需改本机 `.env` 中对应那一行，代码无需改动。真实凭据只放 `.env`，仓库只保留 `.env.example`。
