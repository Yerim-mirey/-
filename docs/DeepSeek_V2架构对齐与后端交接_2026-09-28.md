## 给接手者的任务

请先逐项阅读本交接文档和上面的原始架构文档，然后检查当前工作区中的 V2 实现。目标是让 V2 最新能力继续放在原架构规定的目录和层次中，尤其保证 **Runtime 通过 `app/agent_tools/` 的 Gateway 调用确定性工具**。

不要自行另起一套架构，不要改写 V1 已有 Contract/Schema，不要让 Agent 或 Runtime 直接调用百度 Provider。先指出实际问题，再做必要、范围明确的修复；每项修复均应有对应离线验证。不要因为“全国设施覆盖”目标而把未知数据推断成没有设施或声称人口覆盖结论。

## 原定架构和 V2 现在的位置

原架构的核心职责是：

```text
用户请求
  → Agent Runtime（管理状态与流程）
  → Orchestrator（理解请求）
  → Tool Gateway（Agent 与工具之间的稳定边界）
  → Core Tool / Service（确定性事实与计算）
  → Provider（百度等外部服务）
  → 结构化证据
  → Planning Agent / Reviewer Agent
  → Runtime 汇总结果
```

V1 现有结构继续作为基线：

```text
app/
├── modules/          # 确定性 Tool / Service
├── agents/           # Orchestrator、Planning、Reviewer
├── agent_runtime/    # Runtime、Graph、State、Conditions
├── agent_tools/      # Gateway；隔离 Agent/Runtime 与 Core Tool
├── schemas/          # 版本化契约
├── providers/        # 百度、LLM 等外部服务适配器
└── api/              # HTTP 接口
```

当前 V2 已按相同边界增加对应文件，没有新建顶层架构目录：

| 原有架构职责 | V2 文件/目录 | 当前用途 |
| --- | --- | --- |
| Agent | `app/agents/orchestrator_v2.py` | 解析用户意图、地点、目录设施、全目录范围和待澄清项 |
| Agent | `app/agents/planning_v2.py`、`app/agents/reviewer_v2.py` | 形成规划建议并审查；规划依赖证据，未经审查的建议不返回 |
| Runtime | `app/agent_runtime/runner_v2.py` | 管理单次运行、阶段顺序、时间预算、证据装配、限制和最终回答 |
| Gateway 接口 | `app/agent_tools/gateway_v2.py` | 声明 Runtime 可调用的 V2 工具边界 |
| Gateway 适配器 | `app/agent_tools/mvp_gateway_v2.py` | 把 V2 Gateway 方法映射到现有 Service 和共享百度 Provider |
| Core Tool / Service | `app/modules/poi/`、`app/modules/diagnosis/service_v2.py`、既有 `location/` 与 `routing/` | 设施目录检索、诊断规则、位置和路线计算 |
| 数据目录 | `app/modules/poi/facility_catalog.json`、`facility_catalog.py` | 45 类设施、同义词、能力标记与指标支持范围 |
| Schema / Contract | `app/schemas/*_v2.py`、`contracts/v2/` | V2 请求、结果、任务和示例；V1 契约保留 |
| API | `app/api/v2.py`、`app/api/agent_jobs_v2.py` | V2 目录、工具接口和异步 Agent Job |
| 测试 | `tests/*v2*.py`、`app/modules/poi/tests/` | 目录、服务、Runtime、Gateway、API 和契约验证 |

`app/agent_runtime/runner_v2.py` 现在以 `ToolGatewayV2` 作为位置、POI、探索查询、路线和诊断的唯一工具入口；真实服务在 `MVPToolGatewayV2` 中装配。Gateway 负责将现有 V2 Service 组合成 Agent 可用的稳定接口，Runtime 仍负责何时调用、如何组织证据和何时进入规划/审查。V1 仍走 `ToolGateway` / `MVPToolGateway`，不应为适配 V2 而破坏 V1。

## 目前进度

### 已有能力

- 45 类生活设施统一目录，目录外的明确设施可以走探索查询；探索结果不进入标准设施计数、诊断和规划。
- 全目录检索优先查询各类别主词，再在预算内优先补查用户明确重点、主词无结果或结果较少的类别。单次 POI 检索最多 60 个关键词，单次 POI 检索预算 3 分钟；完整 Agent Run 预算 8 分钟。
- 对检索到点位的类别抽取最多 20 个步行路线目标；未检索到、部分检索或因限额未检索的类别保留对应状态，不将未知当成零。
- 当前标准诊断指标只覆盖菜市场、药店和小学。没有等时圈/人口覆盖证据采集器，因此不输出人口覆盖率或完整供需判断。其他目录设施可回答可用的地图点位和路线信息。
- 规划证据不可用时跳过规划模型调用；路线抽样先选择实际有检索点位的设施类别。
- V2 已通过 Runtime 依赖 Gateway 的离线回归：最近一次记录为 **724 passed、4 skipped**。该测试结果来自本地离线环境，不代表百度/DeepSeek 实时链路或全部设施数据通过真实验收。

### 最近一次真实测试的限制

2026-09-28 对北京学院路做过一次 V2 全目录综合请求。使用已知坐标省掉一次地理编码后，实际消耗 8 次地图请求和 2 个步行路线目标，共 10 个配额单位。百度 POI 返回 `RATE_LIMITED` 后停止补查：共得到 7 个点位；2 类完整、1 类部分、42 类不可用。它不能说明这些类别没有设施，也不能作为全目录验收。运行后发现的问题已经用离线回归修复；修复没有再通过百度重跑。

报告：`docs/test-report/v2-adaptive-search-2026-09-28.md`。

## 接手时先做的架构检查

1. 阅读冻结架构、`app/agent_tools/gateway.py`、`app/agent_tools/mvp_gateway.py`、`app/agent_tools/gateway_v2.py` 和 `app/agent_tools/mvp_gateway_v2.py`。确认 V2 Gateway 是原 Gateway 边界的版本化延伸，没有另造并行事实层。
2. 检查 `app/agent_runtime/runner_v2.py`：它应只依赖 Agent、Schema、目录和 Gateway 接口；不应 import `Baidu*Provider`、直接构造 POI/Location/Routing/Diagnosis Service 或自行请求网络。
3. 检查 `MVPToolGatewayV2.from_baidu_ak()`：位置、POI、路线 Provider 应复用 `build_live_providers()` 生成的同一份按 AK 配额守卫；缺少 AK 时应走明确的 Provider 不可用结果，不能偷偷联网。
4. 保持新的领域文件位于原架构规定的层内。不要把设施目录或诊断逻辑移进 API、Agent 或 Runtime；不要把工作流决策放到 Gateway/Provider。
5. `README.md` 仍有旧句称 `runner_v2.py` 直接组合 Service、尚未接入 Gateway。验证代码后请更新该处和相关交接文字，使文档与代码一致。不要修改原始架构文档中的冻结目标来迁就实现。

## 真实链路验证

真实验证必须和离线测试分开记录。上次百度已触发限流；在没有确认额度可用前，不要循环重试、批量扫词或重复运行整题。可先检查 `/api/v2/facilities` 目录接口和离线测试。额度恢复后，一次性执行一个综合请求，并记录实际地图请求/路线目标数量、运行耗时、各类别的 `complete` / `partial` / `unavailable` 状态、规划/审查状态及限制说明。任何 `unavailable` 都不能写成“该地区没有这种设施”。

API 本地启动方式见 `README.md`。V2 异步接口为：

```text
POST /api/v2/agent/jobs
GET  /api/v2/agent/jobs/{job_id}
```

任务返回的 `completed` 只说明流程结束；最终报告还要检查 `result.answer`、`result.limitations`、错误、设施状态、规划建议和审查结果。不可为了得到“完整”字样而隐藏部分结果或把未知改成零。
