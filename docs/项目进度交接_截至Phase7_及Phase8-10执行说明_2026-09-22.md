## 1. 项目背景与系统边界

项目面向社区 15 分钟生活圈的设施查询、步行可达性、服务盲区体检和规划建议。用户提供地址、街道或明确的 BD09LL 坐标，系统应把自然语言需求转成结构化任务，调用确定性的地图与空间分析 Tool，再基于可追溯的证据给出建议与审查结果。当前公共设施范围只有 `market`（菜市场）、`pharmacy`（药店）和 `primary_school`（小学）。标准体检参数包括 15 分钟即 900 秒、1000 米步行服务距离、200 米网格；实际数值以请求/Tool 契约为准。

**职责分层：** Core Tool 负责事实与 GIS 计算；Orchestrator 理解任务；Planning 根据证据提出建议；Reviewer 审查建议；Runtime 决定执行顺序、重试、返工和终态。Agent 不应直接访问百度 Provider，也不应自己计算等时圈、路由和盲区。完整规划路径如下：

```text
用户消息 → run_agent / Runtime
  → Orchestrator → LifeCircleBrief
  → ToolGateway → Tool 1–6 → EvidenceBundle
  → Planning → PlanningProposal
  → Reviewer → ReviewResult
  → Runtime：完成 / 返工 / 补证据 / 带限制完成 / 失败
```

必须保留数据语义：**`0` 是确认数量为零；`null` 是未知或结果不完整。** `DiagnosisResult.root.ok=true` 只代表返回了合法的成功 Envelope，不能单独证明每个内部阶段都完整，更不能自动等同于正式验收通过。

## 3. Phase 7 实际交付内容与边界

设计和任务记录分别在 [Phase 7 设计](superpowers/specs/2026-09-22-graph-runner-design.md) 与 [Phase 7 实施计划](superpowers/plans/2026-09-22-graph-runner.md)。`fefb424` 添加声明式 Graph，`a3dd1c0` 添加 Runner 和测试。

- [`graph.py`](../app/agent_runtime/graph.py) 定义 `ORCHESTRATE`、`FETCH_EVIDENCE`、`PLAN`、`REVIEW`、`FINALIZE` 及转移表。分支含义由 [`conditions.py`](../app/agent_runtime/conditions.py) 判断，图只映射节点；信息不足进入 `waiting_for_input`。
- [`runner.py`](../app/agent_runtime/runner.py) 的 `run_agent(...)` 是 Python 调用入口。它创建 `AgentRunState`，调用 Orchestrator，先解析地点；普通取证走 Location + POI，完整体检走 Diagnosis；再按需调用 Planning 和 Reviewer。
- Runner 根据实际 Tool 返回值建立 `EvidenceBundle` 和 JSON Pointer 引用。Diagnosis 与低层 Tool 结果不能混装在同一个 Bundle。状态统一通过 [`state.py`](../app/agent_runtime/state.py) 的 `update_run` 更新；证据或提案更换时清除旧下游结果。
- `retryable=false` 的 Tool 失败直接终止；可重试失败在预算内重取；审查要求修改时进入下一轮 Planning，要求补证据时在预算内重新取证；预算或规划轮次上限导致 `with_limitations`。顶层异常转成 `failed` 状态。Phase 7 的执行是内存内单次 Run，不含持久化或跨请求恢复。
- [`tests/test_agent_graph.py`](../tests/test_agent_graph.py) 与 [`tests/test_agent_runner.py`](../tests/test_agent_runner.py) 覆盖节点跳转、等待输入、普通取证、规划通过、重试、失败、返工及补证据回路。测试使用受控模型输出及 Mock/Fake Gateway；**不等于 Phase 8 的完整端到端场景矩阵，也不等于真实模型或百度服务评测**。

**Phase 8 必查的现存边界：** `LifeCircleBrief` 支持 `accessibility_query` 与 `blindspot_query`，但当前 Runner 在 `needs_full_diagnosis=false` 时只装配 Location + POI。若面向用户支持这两类具体问题，Phase 8 必须验证它们取得了相应的路由/盲区事实；若无法在本阶段补齐，就要明确限制受支持意图并让结果不能假装已经回答了可达性或盲区问题。不要仅凭 Run 的 `completed` 判定答案充分。

## 5. Phase 8：Mock E2E 具体要做什么

### 5.1 目标与交付物

用**受控 `StructuredLLM` + `MockToolGateway` + 真正的 `run_agent`**，从一条用户消息运行到 `AgentRunState` 终态，证明多个组件之间的输入输出、状态清理和分支一致。Phase 7 单元测试已证明局部路径，Phase 8 要建立按业务场景组织的完整验收矩阵。建议产物：`tests/e2e/test_agent_mock_e2e.py`、必要的 `tests/fixtures/agent_e2e/` 场景数据、Phase 8 测试说明/报告、README 中的运行命令与能力边界。路径仅是建议，不先预建空目录。

### 5.2 实施步骤

1. **冻结场景输入与预期。** 每个场景写明用户消息、受控模型的 Brief/Proposal/Review 输出、Mock Tool 请求及响应、预期 Tool 调用序列、最终 `status`、`completion_mode`、重试次数、规划轮次与证据引用。Mock 请求必须按 `MockToolGateway` 的规范化请求精确匹配；如果采用自定义样例，保持 v1 Schema 和同请求同返回约束。
2. **建立可复用的测试装配。** 复用现有 Agent、`run_agent`、`load_contract_exchanges()`；受控模型只返回预设 JSON 对象并记录角色调用。测试不要复制 Runner 决策逻辑，也不要用真实网络。场景缺少 Mock Exchange 时应有明确失败，不以宽松兜底掩盖请求差异。
3. **逐场景验证整条状态链。** 除最终状态，还核对 Brief、Evidence、Proposal、Review 的 ID 和轮次，`EvidenceRef.json_pointer` 能在对应 Tool Result 中解析，引用的设施类型和诊断指标与请求一致，warnings/errors 被保留。补证据后旧 Proposal/Review 不得继续有效。
4. **处理具体意图的证据充分性。** 对 `facility_query` 验证 POI；对 `community_diagnosis` 与 `planning_analysis` 验证 Diagnosis；对 `accessibility_query`、`blindspot_query` 分别验证路由/盲区证据。当前 Runner 对后两者只提供 POI，应在 Phase 8 明确修复取证路径，或限制产品支持范围并明确返回不能回答；不要把 POI 数量当作步行可达或盲区结论。若需要改 Runner，仍以 Tool Gateway 为边界，先写失败测试，再作最小改动。
5. **跑全套离线测试与契约校验。** 不设置 `BAIDU_MAP_AK` 和 `RUN_BAIDU_SMOKE`；保存运行命令、测试数和未覆盖项。Phase 8 结束前复核 `README.md`、阶段报告与相应测试是否一致。

### 5.3 至少覆盖的场景矩阵

| 场景 | 期望的关键断言 |
| --- | --- |
| 缺地点或设施类别 | 终态 `waiting_for_input`；没有任何 Tool、Planning、Reviewer 调用。 |
| 普通设施查询 | Location → POI；终态 `completed/normal`；POI 计数与证据引用正确。 |
| 无设施与未知数量 | `0` 与 `null` 分开断言；部分 POI 要有 warning，不从未知推出“没有设施”。 |
| 完整体检 | 通过 Diagnosis 获取三类设施指标；不在 EvidenceBundle 中混装低层结果。 |
| 规划建议被批准 | Diagnosis → Planning → Reviewer；Proposal 和 Review 身份/证据 ID 对齐，终态 `completed/normal`。 |
| 审查要求修改 | 第二轮 Proposal/Review 使用新轮次；旧审查结果被清除；不超过 3 轮。 |
| 审查要求补证据 | 在预算内重新调用 Tool、更换 Evidence、清除旧 Proposal/Review；预算用尽时 `completed/with_limitations` 且有说明。 |
| Tool 可重试失败后成功 | 调用次数和 `tool_retry_count` 与约定一致；最终无半成品证据。 |
| Tool 不可重试/重试耗尽/未配置 Mock | 终态 `failed`，有可定位的 error；不能返回伪成功证据。 |
| 可达性与盲区具体提问 | 结果必须由相应 Tool 事实支撑，或明确标为当前不支持/证据不足。 |

**Phase 8 完成判据：** 上述矩阵有自动化测试且全部离线通过；没有联网或真实模型依赖；关键 JSON Pointer、未知值、状态失效、回路上限被断言；文档准确说明仍不代表真实服务质量。若发现 Phase 7 缺陷，应在 Phase 8 修复并留回归测试，不能直接跳到 Phase 9。

## 6. Phase 9：MVP Tool Gateway 具体要做什么

### 6.1 目标与接口约束

实现 `ToolGateway` 的真实适配器，使 Runner 注入这个 Gateway 后能够调用**现有 Core Service**，无需重写三个 Agent 或 Graph。建议文件 [`app/agent_tools/gateway.py`](../app/agent_tools/gateway.py) 同目录下的 `app/agent_tools/mvp_gateway.py`，配套 `tests/test_mvp_tool_gateway.py`。Phase 9 先以本地假 Provider/受控 Service 做离线验证；真正联网验收留给 Phase 10。

| `ToolGateway` 方法 | 应映射的现有 Core 入口 | 关注点 |
| --- | --- | --- |
| `resolve_location` | `app.modules.location.service.resolve_location` | 地址需要 geocode Provider；坐标应原样保留 BD09LL 中心。 |
| `search_pois` | `app.modules.poi.service.POIService.search` | 保持请求设施顺序、半径、整数与 `null` 的计数语义。 |
| `calculate_walking_times` | `app.modules.routing.service.RoutingService.route` | 保持 target ID、步行模式、不可达和 Provider 错误语义。 |

| `detect_blindspots` | `app.modules.blindspot.service.analyze_blindspots` | 注入路由函数；保留未知网格，不能把未知当盲区。 |
| `diagnose_community` | `app.modules.diagnosis.service.diagnose` | 注入前五个 Tool 所需调用；复用现有高层编排，不让 Gateway 自己重算 GIS。 |

### 6.2 实施和验证顺序

1. 核对六个 Tool 的真实函数签名、Result Envelope、现有 API 依赖组装与 `ToolGateway` 协议。决定一次性构造 Provider/Service 的工厂与生命周期，避免每个方法重复创建网络客户端。服务器 AK 从环境读取，不能硬编码或进入前端。
2. 实现六方法适配器和必要的依赖注入；把受控假 Provider/Service 用于离线测试。方法应返回对应 v1 `LocationResult`、`POISearchResult`、`RoutingResult`、`IsochroneResult`、`BlindspotResult`、`DiagnosisResult`，保留 `ok`、error.retryable、warning、meta。预期错误应经 Tool Result 表达；适配器不自行决定 Agent 重试或规划回路。
3. 复用 [`tests/test_mock_tool_gateway.py`](../tests/test_mock_tool_gateway.py) 的通用契约检查，建立对 Mock 和真实适配器可复用的请求/响应断言；再增加六方法定向映射、Diagnosis 调用链、Provider 失败、部分结果与 `0/null` 的离线测试。
4. 用 Phase 8 已通过的端到端场景，至少跑一个“替换 Gateway 而 Agent 与 Runtime 代码不变”的离线流程。若真实 Core 返回的语义无法准确映射现有 v1 Contract，明确记录差异并先升级契约和测试，不偷偷丢字段或把部分结果转换成完整结果。
5. 更新 README 的 Gateway 选择和配置方式；保持默认测试完全离线，不因导入/构造真实 Gateway 就自动访问百度。

**Phase 9 完成判据：** 六方法都可被同一个 Runner 注入使用；对应 v1 Schema 与交换约束通过；离线模拟的正常、部分、失败路径都保留语义；Agent/Graph 不因 Gateway 更换而改写。**Phase 9 不以真实百度正式验收通过为宣称条件**，但 Phase 10 必须先解决真实服务限制。

## 7. Phase 10：Real E2E 具体要做什么

### 7.1 必须先满足的条件

1. **真实模型适配器。** 当前 [`app/providers/llm.py`](../app/providers/llm.py) 只有 `StructuredLLM` 协议，没有任何模型 API 适配器。选定实际模型服务后，实现结构化对象输出、超时、网络错误与无效 JSON 的明确处理，并通过同一接口注入 Orchestrator、Planning、Reviewer。不能把受控模型测试当作真实模型评测。
2. **百度服务与额度。** 确认服务端 AK 的步行路线服务权限、配额和限流状态。2026-09-19 的正式 Tool 1–6 验收因为步行路由限流记录 `formal_acceptance_passed=false`，即使 Diagnosis Envelope 为 `ok=true`、POI 检索有结果，也不能据此宣称 Real E2E 通过。重试前核对 [正式验收报告](test-report/tool1-6-formal-acceptance-2026-09-19.md) 的配置和保护条件。
3. **Phase 8–9 离线基线通过。** 用相同的公共契约、Runner 和 Gateway 跑通 Mock E2E 及 MVP Gateway 离线替换测试，再启用真实网络。真实凭据仅在本机/部署环境，报告中只保留去敏公开摘要。

### 7.2 分层联调顺序

1. **Tool 层受控重验。** 先执行一次同参数的真实 Core 诊断，记录 Location、POI、Routing、Isochrone、Blindspot 五个阶段、三类设施计数、搜索半径、几何有效性、未知网格、质量和 warning。只有全部满足既定条件才将 Tool 正式验收改为通过；否则保留失败报告并停止扩大调用量。
2. **模型单角色评测。** 用一小组去敏的真实/模拟用户话术，分别检查 Orchestrator 的意图与设施提取、Planning 的证据引用与局限说明、Reviewer 对错误数字、无证据建议和未知值的识别。记录每个失败样例并修提示词或确定性校验。模型服务错误与无效输出应产生明确 `failed`，不能转成假 `approved`。
3. **完整 Agent 路径。** 通过真实模型 + `MVPToolGateway` + `run_agent` 分别走普通查询、完整体检、规划通过，以及至少一个返工或补证据路径；核对真实 Tool 结果、证据指针、规划/审查 ID、终态和用户可解释的限制。额外覆盖地址解析与 BD09LL 坐标两种入口；地址路径不能靠偶然相同中心蒙混通过。
4. **边界和故障演练。** 检查无 AK、模型超时、百度限流、部分 POI、路由不可用、用户信息不足的结果。`ok=true` 的部分诊断应保留 `partial/unavailable` 与 `unknown`，不能说成完整覆盖；`failed` 和 `with_limitations` 不应渲染成正常成功。
5. **形成验收报告。** 记录 Git 提交、配置口径、样本/场景、调用量保护、通过/未通过项、警告、失败原因与复验条件。报告不得包含 AK、原始敏感百度响应、请求 URL 或个人信息。必要时再增加 API/界面入口；当前 `/api/v1/diagnosis` 不是 Agent API，不能把调用 Core API 当作 Agent Real E2E。
